# 규칙 검사

`src/rules/`의 규칙은 글을 받아 위반 목록을 돌려주는 순수 함수다. LLM을 쓰지 않으므로 같은 글에는 항상 같은 결과가 나온다. 이 문서는 규칙 목록과, 코드만 봐서는 알 수 없는 판단의 이유를 적는다.

## 심각도

| 심각도 | 의미 | `passed` 판정 |
|---|---|---|
| `error` | 규칙 위반이 확실함 | 실패 |
| `warning` | 위반일 가능성이 높음 | 실패 |
| `info` | 참고. 지금은 이 심각도를 내는 규칙이 없음 | 영향 없음 |

## 규칙

| id | 잡는 것 | 심각도 |
|---|---|---|
| `frontmatter` | JSON Schema 위반, frontmatter 없음, YAML 오류, 없는 `thumbnail` 파일 | error |
| | 스키마에 없는 필드 | warning |
| `footnote-integrity` | 표시와 설명 줄의 짝이 안 맞음, 설명 줄 중복 | error |
| `footnote-placement` | 참고 자료 절이 없음, 절 밖의 설명 줄, 절 뒤의 다른 절 | error |
| `footnote-link` | 설명 줄에 링크가 없음, http(s)가 아닌 링크 | error |
| `footnote-length` | 링크를 뺀 설명이 150자 초과 | warning |

입력과 출력의 예다.

```md
본문.[^1] 다른 문장.[^2]

## 참고 자료

[^1]: 설명. — [제목 - 출처](https://example.com)
[^1]: 또 쓴 설명. — [제목 - 출처](https://example.com)
[^3]: 설명. — [제목 - 출처](https://example.com)
```

```
[error] footnote-integrity: [^2] has no definition
[error] footnote-integrity: [^1] is defined twice (first at line 5)
[error] footnote-integrity: [^3] is never used in the body
```

## 설계 판단

### 스키마를 복사하지 않고 사이트에서 읽는다

사이트의 스키마는 `astro:content`에 묶여 있어 다른 프로그램이 import할 수 없다. 복사하면 사이트만 고쳤을 때 어긋나고, 다른 사이트에 쓸 수도 없다. Astro가 스키마를 JSON Schema 파일로 내보내므로 그 파일을 읽는다. JSON Schema는 표준 형식이라 다른 사이트도 파일만 만들면 된다.

단, 이 파일은 생성물이다. 사이트 스키마를 고친 뒤 다시 만들지 않으면 예전 스키마로 검사한다.

### 검사기로 `ajv`를 쓴다

두 방법을 실제 글 35편으로 비교했다.

| 검사기 | 통과한 글 | 이유 |
|---|---|---|
| zod `fromJSONSchema` | 0편 | `pubDate: '2026-10-30'`을 날짜-시간 형식이 아니라고 거부 |
| `ajv` (날짜 형식 완화) | 35편 | |

사이트는 `z.coerce.date()`로 날짜를 읽는데, 내보낸 스키마에는 `date-time` 형식으로만 남는다. 그래서 날짜 형식은 `new Date()`로 읽을 수 있는지만 보도록 바꿨다. `ajv` 오류는 분기(`oneOf`)의 모든 갈래를 보고하므로, `const`가 어긋난 갈래의 오류는 걸러 낸다.

### frontmatter를 먼저 잘라 낸다

frontmatter는 정규식으로 잘라 YAML로 해석하고, 본문은 따로 remark로 파싱한다. Astro도 같은 구조이고, 정규식도 Astro의 것에서 TOML만 뺐다. 그래서 frontmatter를 인식하는 기준이 사이트와 같다. frontmatter가 깨져도 본문 규칙은 계속 돌아간다.

잘라 낸 자리는 지우지 않고 공백으로 채운다. 본문의 줄 번호와 오프셋이 원문과 같게 유지되어 위반 위치를 그대로 보고할 수 있다.

### 본문을 파서로 읽는다

본문의 `[^1]`이나 `##`은 코드 블록 안에 있으면 각주나 제목이 아니다. 정규식으로는 이를 구분하지 못한다. 단, 짝이 없는 표시는 remark가 평문으로 남기고, 이미지 캡션 안의 표시도 노드가 되지 않으므로, 이 둘은 텍스트와 이미지 노드의 원문에서 따로 찾는다.

### 길이 기준은 150자다

인물, 회사, 논문, 기술을 소개하는 각주를 직접 써서 세어 보면 한 문장에 70~77자이고, 약력을 한 문장 더 붙인 실제 각주는 116~117자다. 실제 글 172개 각주의 중앙값은 44자, 최대는 131자다. 정상적인 소개 각주는 통과시키고, 각주에 문단을 쏟아붓는 경우만 잡도록 150자로 정했다.

### 절 이름은 템플릿에서 읽는다

참고 자료 절의 이름은 코드에 고정하지 않고 `RuleContext`로 넘어온 템플릿에서 읽는다. 규칙은 파일을 직접 읽지 않고 `assetExists`로 묻기 때문에, 테스트에서 가짜 템플릿과 가짜 파일 확인을 넘길 수 있다. 템플릿의 `sections`는 M4 초안 작성에서 쓸 안내용 값이라 검사하지 않는다.

## 넣지 않은 검사

처음에 검토했지만 실제 글을 돌려 보고 뺀 검사다.

| 검사 | 실제 글 결과 | 빼는 이유 |
|---|---|---|
| 각주 번호와 설명 줄의 순서 | 6편 warning | remark가 화면의 번호를 처음 나온 순서대로 다시 매기므로 독자에게 영향이 없음 |
| 참고 자료 절의 제목 깊이 | 0편 | 글 구조에 따라 달라질 수 있음. 절이 있고 끝에 있는지만 보면 충분함 |
| em dash 구분자, 설명의 마침표 | | 독자에게 영향이 없는 표기 차이 |
| 설명 없이 링크만 있는 각주 금지 | 2건 | 사전 항목 링크처럼 설명이 필요 없는 경우가 있음 |
| 링크 글자의 ` - 사이트이름` | 6건 | 링크 주소에 이미 출처가 드러남 |
| 설명 40자 미만 | 71건 | 전체의 41%가 걸림. 짧다고 해서 문제가 되지 않음 |
| 같은 표시를 다시 붙임 | 19건 | 한 출처가 뒷받침하는 주장이 여러 번 나오면 자연스러움 |
| 인용, 수치, 쪽 번호, 나열, 표 | 12건 | 각주에 있을 수 있는 내용이고, 패턴 추정이라 오탐이 많음 |
| 이미지 캡션의 각주 금지 | 4건 | 사이트가 캡션의 각주를 지원하며, 저작권 표시에 쓰고 있음 |
